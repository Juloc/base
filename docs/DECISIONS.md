# Decisions

Small decisions made while building, one sentence each with its reason. Newest last. The big ones are in `docs/BASE.md` of the JulOS repository.

## 0.1.0 (2026-11-23)

1. **English everywhere in the repository** (docs, comments, log lines, error messages of the server); German and English only in what a person sees: one language for the people and agents who read code, as in the JulOS docs.
2. **An app carries the base in a folder `base/`** (C# modules, `ui/`, rulebook, `VERSION`, `MANIFEST`) and references the projects there: one folder that is plainly "not ours to edit", and a checksum per file makes drift visible.
3. **The base modules keep their names (`Base.Core` ...) in every app; only the start project is renamed:** a copy that is byte for byte the base can be compared and renewed by a script.
4. **The look is embedded in `Base.Web` and served under `/base/`:** an app has exactly the look of the base version it was built with, and nothing has to be copied into its `wwwroot`.
5. **Migrations come in sets (`accounts`, `web`, `app`), applied set after set:** each module owns its tables, and an app's numbers never collide with those of the base.
6. **An applied migration is protected by a checksum:** the rule "never edit an applied script" fails loudly at start instead of silently producing two different schemas.
7. **The server answers failures with a code, the browser translates it:** the server does not need to know the language of the reader, and a test can check that every code has a text.
8. **The key for encrypted values is required** (a file in the data folder, made at the first start), unlike JulOS where it was optional: an app without it would store the authenticator secret in plain text.
9. **The Compose file uses one volume with three sub-folders** (database, the server's key, the database password) and a one-shot init step from the PostgreSQL image: one thing to back up, no variables, and a random database password instead of one written into the file. It needs Docker Engine 26 or newer (volume sub-paths).
10. **The database password is random per installation although the database is not published:** it costs one init step and removes the only secret-like value a Compose file without variables would otherwise contain.
11. **The session cookie is named after the app (`<id>_sid`):** cookies do not know ports, so two apps on one host name would otherwise sign each other out.
12. **Lockout counters and a requested-but-unconfirmed authenticator live in memory:** a restart only clears waits of at most 15 minutes, and no table is written on every failed attempt. Sessions themselves are in PostgreSQL.
13. **The first account gets the role `admin`; roles are a `text[]` on the person:** enough to guard the settings of the installation now, and open for roles per app later.
14. **Trusted proxies default to "every private network" until set in the app,** as in JulOS: an app behind a reverse proxy on the same host works without setup; the settings page says how to restrict it.
15. **`/api/health` answers 503 when the database does not answer** (JulOS answered 200 with `ok: false`): proxies and monitors read the status code.
16. **JSON of the base's endpoints is source-generated, an app's own types use reflection:** the base stays fast and explicit, and an app author does not have to register every type.
17. **Colours are `oklch()` with fixed lightness per role and the hue from one variable (`--accent-hue`), light and dark through `light-dark()`:** contrast is decided by lightness, so it can be tested once for all 360 hues; it needs browsers from 2024 on.
18. **The contrast test takes the worst of three renderings** (wide gamut as it is, clipped to sRGB, chroma lowered): browsers differ in how they show a colour outside sRGB.
19. **Controls are 44 px high by default and 36 px only on a wide screen that is not driven by a finger** (`not (pointer: coarse)`): the phone is the default, and a tablet keeps finger sizes.
20. **A dialog is a non-modal `<dialog>` (`show()`), movable on a wide screen, a sheet on a phone,** also for confirmations: the owner wants dialogs that never block the page.
21. **`base.js` contains a tiny hash router and the shell:** every app needs both, and without them each app would grow its own.
22. **The service worker keeps what was fetched as a fallback and has no list of files:** nothing to maintain, updates arrive at once, answers of the API are never kept.
23. **App icons are SVG only for now** (no PNG sizes): enough for installing on Android and desktop; iOS wants a PNG, which comes with the first real app.
24. **Step-up (a fresh second factor for dangerous actions) was not taken over from JulOS yet:** its policy table is specific to JulOS; it returns when the second app needs it.
25. **The rulebook has 50 rules and one level word per rule (MUST, SHOULD, MAY for Muss, Soll, Kann):** only rules the base keeps today, most with a test.
26. **`scripts/sync-base.sh` exists although only `new-app.sh` and `check-app.sh` were asked for:** it is the same copy function, and a drift check without a way to renew the copy would be half a tool.
27. **The made app has no test project of its own yet:** the tests of the base cover the base; what an app must test of its own is decided with the first real app.
28. **Roles stay a text array in the table but a person holds exactly one:** the column came with 0.1.0 and apps may already have data; a second table or a column rename would buy nothing. `RequireRole` and the checks read the one entry; the list is `UserRow.Role`.
29. **The role is declared on the endpoint (`RequireRole`) and checked by the guard, not in the handler:** the check cannot be forgotten and a test can list every admin endpoint from the endpoint table.
30. **An invitation link carries its token in the fragment (`/#invite=...`) and the token is hashed in the table:** a fragment never reaches a server, a proxy or a log; the table cannot be used to join. One link per person at a time, so a new link kills the old one.
31. **Blocking, deleting and demoting run one at a time in the process (a semaphore), not under a database lock:** an app is one container (OPS-01); the last-admin rule is then a simple count and the concurrent case is tested.
32. **A person of the hub cannot get their role changed in the app:** the hub decides and overwrites it at every sign-in, so a local change would silently vanish; the list shows where the person comes from. Blocking and deleting stay possible.
33. **The hub flow is our own code on Microsoft's token library, not the OpenID Connect handler:** the handler keeps its state in Data Protection keys and correlation cookies, which in a container are lost at an update, and it would bring a second session system; our flow keeps state, nonce and verifier in a table for ten minutes, and the library only checks signatures and claims.
34. **ES256 only, and one reading of the keys per minute at most on an unknown key:** JulOS signs with ES256; fixing the algorithm closes the "none" and symmetric-key attacks, and the limit stops a stream of tokens from turning into a stream of requests to the hub.
35. **No `id_token_hint` at sign-out, because no token is kept:** the hub asks the person first (its rule). Keeping the token only for this would be the wrong trade.
36. **Hub settings live in `instance_settings` under keys no generic rule knows:** the generic settings API neither lists nor writes them, so the secret cannot leak through it; they have their own admin endpoints with their own checks.
37. **The name on the button comes from the hub's anonymous `/api/about`, else the host name:** JulOS has no anonymous `/api/about` yet (its own is behind a session), so for now the button carries the host.
38. **`/api/about` gives `accentHue` (a number), not a colour:** the base knows colours only as one hue (COLOR-01); the hub builds its own tile colour from it. The contract draft's hex colour is left open.
39. **`/api/about` is the one cacheable answer of the API (five minutes, public):** it is the same for everybody and holds nothing private; the contract asks for it.
40. **The ID token of the hub stays on the session as the sign-out hint (nothing else of it):** JulOS signs out without asking and returns the person to the app only for a valid hint; without it the person is stranded at the hub.
41. **The look is that of JulOS, with the kit's own token names:** one family look for the owner's apps; the names stay so apps do not change, only the values (Material 3 roles and tone steps, as in JulOS's `m3.css`).
42. **The tertiary tone is the accent hue turned by 55 degrees (`calc(h - 55)` in the relative colour):** JulOS does the same; the contrast test evaluates the same formula.
43. **Labels stay above the fields and a dialog never has a scrim:** floating labels need script (FORM-01), and a scrim would block the page behind a window that must not block it (DIALOG-01); filled fields and the sheet shape are taken from JulOS otherwise.
44. **Glass is made from the solid surfaces and contrast is tested on the solid ones:** the glass is 66 to 86 percent of a tested surface over a faint gradient, so the pairs hold; with reduced transparency it is the surface itself.
45. **Body text is 16 px and list titles 16 px (JulOS uses 14 px):** the apps are read on wide screens too, and 16 px keeps phone inputs from zooming; secondary text is 14 px.
46. **Lists are tiles, lines are the variant:** one soft tile per row looks like JulOS and Jularr; lines stay for long lists and tables, where tiles would waste the screen (a list inside a `.card`, or `.list.lines`).
47. **The page head is built by `shell()` in the page, not in the bar:** a big title with a second line and the main action at the right is the start page of JulOS; the bar on the phone only carries the app name, then the title once the page scrolls. On a wide screen there is no bar at all.
48. **The pair "accent on surface-4" is tested at 3:1 only:** it is the thickened line under a focused field, a decorative edge next to the 2 px ring (the field itself is told by its label and its text); all pairs that carry text stay at 4.5:1.
49. **Fine edges instead of shadows in dark (`--glass-edge` is the text colour at 13 percent):** that is how Jularr shows depth; a coloured shadow on a deep dark ground looks like a glow. Sheets and menus keep a black shadow because they float over content.
50. **A capsule looks the same for choices (`segmented()`) and for places (`capsule()`):** one part, two meanings; the chosen part is a filled accent pill, so the choice is told by fill and weight, not by colour alone.
51. **The name of the migration table is an option, not a convention that every app must meet:** an app that moves onto the base may already own a `schema_migrations` with other columns; the default stays, and only a plain identifier is accepted because the name goes into SQL text (a table name cannot be a parameter).
52. **A door needs a check, and the type does not allow one without it:** a prefix with a missing or forgotten check would be an open path or one that quietly falls back to the session; with a required check the app has to say, in code, who may come in.
53. **Under a door the session cookie is never read:** a key and a cookie are two kinds of caller that must not be mixed. A cookie that happened to be sent (a browser on the same host) neither opens a door nor gives the handler an identity or a rotated cookie, so a handler under a door cannot act "as the person" by accident, and the door needs no `X-Base` or Origin because no browser session is involved. A check that throws counts as no.
54. **A door cannot lie on a path the base serves or the app declares otherwise:** the first segment may not be one the base uses, and a public or large-body path may not sit under a door, so one path never has two kinds of protection; two doors may not overlap. Refused at start.
55. **A door matches its prefix without regard to case:** the routes of ASP.NET Core ignore case, so `/api/V1/x` reaches the endpoint behind the door `/api/v1`. If the guard compared exactly, that spelling would fall to the session guard and a signed-in person's cookie would open an endpoint that trusts the door's key. Found in the read-through before release; `DoorTests.Another_spelling_of_the_path_is_still_the_door`.
56. **The role of a person changes in one place, `UserStore.TrySetRoleAsync`, and the last-administrator check is part of the statement:** the administrator's change and the sign-in through the hub both use it, so the rule cannot be forgotten in a new way to change a role. When the hub's role is not applied the sign-in still works (the person is who the hub says) and the history records why.
57. **The first setup is closed by any account that can sign in, a person of the hub included:** counting only confirmed authenticators made an installation of hub people look empty. A fresh installation has none, so its first start is unchanged.
58. **The service worker has a list of shell files (this replaces the "no list of files" of 22):** keeping every GET outside `/api/` would also keep pages that need a session and show them after sign-out; a short list in one file is the smaller cost.
59. **A body limit is declared on the endpoint (`WithMaxBody`) and counts only after the session is known:** a path with an id and a file path cannot be listed in `LargeBodyPaths`, and the larger limit must never be a gift to an anonymous caller, so the guard resolves the session first for such an endpoint and answers 401 before it looks at the size. A public path ignores the declaration.
60. **DuckDB is allowed for logs and statistics (CODE-02), on the owner's yes of 2026-11-26:** the first app (caddy) keeps every request of its proxy; in PostgreSQL that is about 116 MB per million rows and slow sums, an embedded column store needs a fraction of the disk and nothing while idle. Only for bulk logs and statistics; an app's own data stays in PostgreSQL.
61. **The accent is a colour, the tokens derive from it with relative colour syntax (0.4.0, owner's decision on caddy):** `--accent-color` (any CSS colour) or, as before, `--accent-hue`; `--accent-base` takes the one that is set, every token is `oklch(from var(--accent-base) L C h)`. A fixed lightness per role is kept, the chroma is capped (`min(c, ...)`) so a strong colour makes a calm surface. Needs Chrome 119, Safari 16.4, Firefox 128 (2024). The contrast test evaluates these formulas itself, for every hue and for hard colours.
62. **The text on the accent fill is black or white by luminance** (`color(from ... xyz-d65 ...)`, threshold at relative luminance 0.1795, where both reach 4.5:1): a tinted dark ink in the lightness of oklch fails for some colours (a violet at lightness 0.58 is better with white), so the test found no safe tint.
63. **Links, focus rings, icons and lines use `--accent-ink`, not the fill** (this changes the "ring in the bright accent" of the design): a light accent such as yellow or cyan does not show on a light page; the bright fill stays for switches that are on, the brand mark and charts. SHOULD-level deviation from the design text, MUST for A11Y-02.
64. **`--warn` (strong amber, oklch 0.70 0.17 75) is not a text colour:** it has no contrast on a light page; text in a warning is `--on-warn-soft`. `--warn` is for dots, bars and icons next to a text. The pair `warn` on `bg` is removed from the contrast lines. Danger text on the filled field (`surface-4`) needs 3:1 only (raspberry at lightness 0.55 gives 4.5:1 on the other surfaces).
65. **The row button is 34 px with a 44 px target:** an invisible `::after` extends the hit area by 5 px above and below (MOBILE-01 asks 44 px for a finger).
66. **The edge of a field is faint (0.4, owner's decision on caddy), so COLOR-02 asks 3:1 for the focus ring and the chosen state, not for the resting edge:** a field, a dropdown, a toggle and a segmented choice are told from the page by their own white surface, a soft shadow and a border of 10 % of the text colour; the label above and the placeholder inside name them. The 3:1 line of the old look (`line-strong`) stays as a token for what has only a line. MUST rule, changed on the owner's word; if a review finds a person who cannot see a resting field, the edge gets stronger, not the rule weaker.
67. **`dropdown()` keeps its value in a hidden input and puts its list on `body`:** a form reads it as before (`formValues`, `change` fires on the input), and the list is not cut off by a dialog or a card that scrolls. The old `<select>` of `field({ type: 'select' })` is gone (Breaking: `field.querySelector('select')` becomes `input[name=...]`, or `.value` on the dropdown element); the `.select` class stays for markup written by hand. The list is a sheet on a phone (below 600 px) and hangs at the button on a wide screen, flipping above when there is more room there.
68. **A dialog stays non-modal with a scrim that only dims:** the owner wants big dialogs with a dimmed page, DIALOG-01 wants the page usable, so the scrim has `pointer-events: none`. A dialog closes on `hashchange` (the router calls `closeDialogs()`), not on a refresh of the same page; an app that navigates by other means calls `closeDialogs()` itself. Size `m` is 720 px, `l` 940 px, `s` 480 px (confirmations).
69. **The menu pill holds every place, and `floatBar()` is `actionBar()`:** SHELL-01 no longer limits the phone menu to five places; the pill scrolls. The selection bar hides the action bar with `:has()` (supported since 2023 in every browser the apps target) instead of a call between them. A dot or count on a place is `navBadge(path, value)`, kept in a map so it can be set before the shell exists. The capsule (links to places) keeps its old outline until the tabs are restyled in step 5.
